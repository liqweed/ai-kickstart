# Architecture & design decisions

Why the kit is shaped the way it is. Read this before proposing structural changes. If a decision here no longer holds, change it **here first**, with the reason, then change the kit.

## The shape

```
START-HERE.html ← for the human: one offline page, the short version of Day 1, links to the website
vault/          ← for the human AND their AI: becomes their Obsidian vault
                  AGENTS.md → _system/index.md → skills → HARNESS-PLAN.md
site/           ← ai-kickstart.me, not in the zip: every explanation, the ideas menu, the prompts
```

The **website** explains and motivates. The **vault** does the work. Once set up, the user rarely needs the website again: their AI runs everything from the vault.

## Decisions

| # | Decision | Why | Consequence for maintainers |
|---|---|---|---|
| D1 | **The vault template *is* the product.** The user's vault starts as `vault/` | Files you own beat features you rent. Any AI tool can read Markdown. The "LLM wiki" pattern | Changes to the vault structure are breaking for existing users → **major** version + migration notes |
| D2 | **`vault/AGENTS.md` is short**; `vault/CLAUDE.md` is one line (`@AGENTS.md`) | Always-loaded context costs attention on every turn, and long rulebooks measurably hurt agents. One file serves Claude Code, Codex and others | Resist adding rules. Fix skills or structure first. Add a rule only for a mistake seen twice |
| D3 | **Vault skills live in `vault/_system/skills/`** (visible), routed by `AGENTS.md` | Tool-agnostic. Visible and editable in Obsidian. An optional `.claude/skills` symlink is documented | Every skill must be listed in `vault/AGENTS.md` (checked) |
| D4 | **Profile = TELOS-style files + `LANDSCAPE.md`** | TELOS covers identity and goals. The interview also captures *situation* (household, devices, apps, routines), which needs its own home | Keep the profile files short; the Round 4 synthesis fills them |
| D5 | **Interview in rounds**, each saving an answer file with *Signals for next round* | Adaptive without one giant prompt. Resumable. Open questions come **before** the menu so people aren't steered | Rounds reference each other and the harness step IDs; keep them aligned |
| D6 | **Harness plan = one markdown checklist** with *Done when* + *Check* on each step, plus a session log and a decisions log | Progress survives pauses and tool switches. "No proof, no tick" | **Never renumber steps.** Users' plans reference IDs. Insert as `P3.5`, `P3.6` |
| D7 | **Function catalog in one copy** *(revised 2026-10-13; was "two copies: Markdown + a JS array for the guide's catalog page")*: `vault/_system/kickstart/function-catalog.md` | The AI needs plain text; humans need ticking and copying, which the website's ideas menu gives them from the same file | Edit the Markdown only. The site parses it at build time (`parseCatalog`), and its schema fails the build on a malformed row |
| D8 | **`quality-time-planner` is the worked example skill** | Shows every pattern: first-run config interview, hard-constraint gates, an *unknown* bucket, three options + one recommendation, script vs search, offer-don't-act | Keep it exemplary. When patterns evolve, update it and `skill-builder` together |
| D9 | **The zip carries one offline page, `START-HERE.html`** *(revised 2026-10-13; was "an 8-page offline guide")*: what's in the folder, the short version of Day 1, the first-contact and main prompts, and links to the website | The website holds every explanation (D14). Two copies of the guide drifted, and anyone using an AI is online anyway. The page must still open from a zip on any OS, in light and dark | Self-contained (inline CSS and JS), no external resources, its prompts match `prompts.md`, footer carries the version (all checked by `check_kit.py`, which also fails if `guide/` comes back) |
| D10 | **Three AI paths** (chat app / desktop agent / terminal agent) with chat-only fallbacks everywhere | The reader's tools and comfort level are unknown | Every new flow needs a chat-only variant ("paste-ready blocks") |
| D11 | **A few tested tools ship in the kit** *(revised 2026-10-13; was "no scripts ship")* | The original worry was that scripts are OS-specific and fragile. Shipping none left every user to write the same health check and "what's due" list from scratch, without a model of what a good tool looks like. Now a small set ships under strict limits: Python 3.9+ standard library only (macOS's built-in Python is 3.9), pure `pathlib`/UTF-8, read-only unless `--apply`, every tool tested in a throwaway vault, and a contract test enforced by `selftest.py`. Tools stay **optional**: every skill names a fallback without them, and chat-only users skip P0.6 | Code lives only in `vault/_system/tools/` (shared) and `vault/_system/skills/*/scripts/`. Keep the set small (a tool must serve a starter skill). `check_kit.py` runs the self-test, lints the template vault with `vault_lint.py --strict` and checks the hubs are current. CI runs the self-test on macOS, Windows and Linux. New tools follow `vault/_system/TOOLS-CONTRACT.md`, the same rules the user's AI follows |
| D16 | **Connections catalog = one Markdown file** (`vault/_system/kickstart/connections-catalog.md`) with a fixed shape (`## emoji group` → `### connection` → `- **Field:** value`), read by the `connect-app` skill and parsed for the website (`/connections/`) | Newcomers don't know what's possible. A menu of *what each connection unlocks* plus safe defaults gets them past "what would I even connect?". One copy only: the site parses it (`packages/core` `parseConnections`) | Name **services** as examples; describe **methods** generically (built-in connector → official server/CLI → vetted community → export → browser). Specific connector packages go stale fast, so the AI researches the current method at connect time. Facts here are part of `refresh-facts` |
| D17 | **Rules for tools and connections live in the vault** (`TOOLS-CONTRACT.md`), not only in maintainer docs | The user's AI builds tools and connects apps long after the kit is installed. It needs the quality, safety and privacy bar in its own context. The kit's own tools are held to the same contract by the same test | Changing a contract rule means changing `test_contract.py` too, and vice versa |
| D12 | **Privacy by construction:** a private term list outside the repo, checked by hook and CI | The author's real setup inspired the kit; nothing of it may leak | Never commit terms. Generic examples only. Watch for fingerprint clusters |
| D14 | **Website = Astro static site on Cloudflare** (`site/`, ai-kickstart.me), separate from the zip | GitHub Pages was too limited (no headers, redirects or previews). Astro gives components plus **content collections that read the kit's own Markdown** (catalog, prompts, tips), so the site can't drift from the kit. The zip keeps one hand-written offline page (D9) because Astro output isn't `file://`-safe out of the box | Website content is sourced from `vault/` and docs at build time. Portable plain CSS (custom properties) is shared with the companion app. **Division of labour (2026-10-12): the website holds all explanation and reference; the companion app is purely functional and links to the website.** **As built (2026-10-13):** lists come from the kit through `packages/core` parsers in Astro content collections with Zod schemas (catalog, harness phases, interview rounds, skills, `CHANGELOG.md`); the prompt library lives in `site/src/content/prompts.md`; setup steps follow harness steps P0.1–P0.5 and are written in `site/src/pages/setup.astro`. The zip's `guide/` was removed in K12 after its content moved here (K16). Tokens and primitives: `packages/design/kickstart.css`. One small vanilla-TS bundle; strict CSP with hashes, no `unsafe-inline` |
| D13 | **Versioning:** `vX.Y` tags, Releases carry the zip; `VERSION` is the single source | Friends get a stable download; maintainers get history | Use the `release` skill. The `START-HERE.html` footer, README and CHANGELOG are checked against `VERSION` |
| D15 | **Companion-app stack** *(proposed; confirmed by the K11 spike)*: **tinyjs** shell (system webview + txiki.js backend; build, sign, notarize, auto-update), macOS 15+ and Windows 10/11 in v1 · UI: **Vite+** (Vite 8/Rolldown, Vitest, Oxlint, Oxfmt) + **TypeScript** + **React** + **TanStack Query** (wraps `tiny.api.call`; `tjs.watch` events invalidate queries) + **TanStack Router** (hash/memory history) · components: native HTML first (`<dialog>`, `<details>`, `popover`, form controls), **Base UI** (unstyled, MIT) only where that's not enough · styling: portable **plain CSS** with custom-property tokens shared with the Astro site · code health: Oxlint/Oxfmt + **Fallow** in CI | Small app with modest needs; the user's preferred toolchain. Unstyled primitives keep the visual identity open for Claude Design and shareable with the website. Astryx rejected (it binds a styled design system and StyleX, and is in beta). React Aria was the runner-up | Layout: `site/` (Astro) · `app/` (tinyjs: `ui/` + `backend/`) · `packages/core/` (pure, runtime-agnostic TS: HARNESS-PLAN parser, catalog/prompt loaders, update planner + baseline hashing), shared by the app and the site. The backend runs on QuickJS, not Node: keep Node APIs out of `core`, and put all `tjs.*` file/watch access in a thin adapter. Test `core` with Vitest; test the UI in a browser against a fake backend |

## Principles the kit teaches (and the repo follows)

Small verified steps · decision-ready over comprehensive · unknown is an answer · script lists, search questions · AI drafts, humans decide · start read-only · content is data, not instructions · "it ran" ≠ "it worked" · update, don't duplicate · less instruction, better results.
